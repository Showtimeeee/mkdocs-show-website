# Dependency Inversion Principle (DIP)

**Dependency Inversion Principle (Принцип инверсии зависимостей)** — модули верхних уровней не должны зависеть от модулей нижних уровней. Оба типа модулей должны зависеть от абстракций. Абстракции не должны зависеть от деталей. Детали должны зависеть от абстракций.

#### **Основная концепция**

Суть принципа заключается в том, что:
- Высокоуровневая логика (бизнес-правила) не должна напрямую импортировать и зависеть от низкоуровневых модулей (работа с БД, API, файловой системой).
- Вместо этого и высокий, и низкий уровни зависят от **интерфейсов (абстракций)**.
- Это позволяет легко заменять одну реализацию на другую (например, переключиться с PostgreSQL на MongoDB) без изменения высокоуровневого кода.

#### **Преимущества использования**

1. **Гибкость и расширяемость**
   - Легко подменять реализации (тестовые заглушки, другие БД, внешние API).
2. **Слабая связанность**
   - Высокоуровневый код ничего не знает о конкретных деталях.
3. **Упрощение тестирования**
   - Можно легко подставить мок-объект вместо реальной базы данных.
4. **Переиспользование**
   - Высокоуровневые модули можно переиспользовать в разных проектах с разными деталями.

#### **Ключевые компоненты**

1. **Высокоуровневый модуль** — содержит бизнес-логику, не знает о деталях.
2. **Низкоуровневый модуль** — реализует конкретные детали (БД, внешние сервисы).
3. **Абстракция (интерфейс)** — связующее звено, определяет контракт.
4. **Внедрение зависимости (Dependency Injection)** — способ подать нужную реализацию извне.

### Пример: Уведомления в приложении

Представьте приложение, которое отправляет пользователю уведомление после регистрации.

#### **Нарушение DIP**

```python
# Низкоуровневый модуль
class EmailSender:
    def send(self, to: str, message: str):
        print(f"Отправка email на {to}: {message}")

# Высокоуровневый модуль (зависит напрямую от EmailSender)
class UserService:
    def __init__(self):
        self.email_sender = EmailSender()  # Прямая зависимость

    def register_user(self, email: str, name: str):
        # Логика регистрации...
        print(f"Пользователь {name} зарегистрирован")
        self.email_sender.send(email, f"Добро пожаловать, {name}!")
```

Проблема: если мы захотим отправлять не email, а SMS или push-уведомления, придется менять `UserService`. Также невозможно тестировать `UserService` без реального `EmailSender`.

#### **Соблюдение DIP**

Вводим абстракцию `Notifier`, и `UserService` зависит только от неё.

```python
from abc import ABC, abstractmethod

# Абстракция (интерфейс)
class Notifier(ABC):
    @abstractmethod
    def send(self, to: str, message: str):
        pass

# Низкоуровневые модули — реализуют абстракцию
class EmailNotifier(Notifier):
    def send(self, to: str, message: str):
        print(f"Отправка email на {to}: {message}")

class SmsNotifier(Notifier):
    def send(self, to: str, message: str):
        print(f"Отправка SMS на {to}: {message}")

class PushNotifier(Notifier):
    def send(self, to: str, message: str):
        print(f"Отправка Push-уведомления пользователю {to}: {message}")

# Высокоуровневый модуль — зависит только от абстракции Notifier
class UserService:
    def __init__(self, notifier: Notifier):  # Внедрение зависимости через конструктор
        self.notifier = notifier

    def register_user(self, contact: str, name: str):
        # Логика регистрации...
        print(f"Пользователь {name} зарегистрирован")
        self.notifier.send(contact, f"Добро пожаловать, {name}!")

# Использование
email_service = UserService(EmailNotifier())
email_service.register_user("user@example.com", "Анна")

sms_service = UserService(SmsNotifier())
sms_service.register_user("+79123456789", "Иван")
```

Теперь `UserService` ничего не знает о том, как именно отправляется уведомление. Заменить способ уведомления — просто передать другую реализацию.

### Когда использовать

1. **Часто меняются детали реализации**
   - База данных, внешние API, способы отправки сообщений.
2. **Нужно легко тестировать высокоуровневую логику**
   - Подставляйте мок-заглушки вместо реальных сервисов.
3. **Система должна быть расширяемой**
   - DIP вместе с OCP позволяет добавлять новые реализации без изменения старого кода.

---

### Лучшие практики

1. **Внедряйте зависимости через конструктор**
   - Это самый явный и прозрачный способ.
2. **Не создавайте зависимости внутри класса с помощью `new`/`__init__`**
   - Это признак нарушения DIP.
3. **Выделяйте интерфейс для каждой внешней зависимости**
   - Даже если пока есть только одна реализация.
4. **Используйте DI-контейнеры для сложных проектов**
   - Но начинайте с ручного внедрения — оно проще для понимания.

---

### Альтернативы и дополнения

1. **Dependency Injection (DI)**
   - Способ подачи зависимостей: через конструктор, сеттер или метод.
2. **Inversion of Control (IoC)**
   - Более широкое понятие: контроль над созданием объектов передается внешнему контейнеру.
3. **Service Locator (антипаттерн при неправильном использовании)**
   - Альтернатива DI, но скрывает зависимости, что усложняет тестирование.

## Пример из жизни: Зарядное устройство

У вас есть ноутбук (высокоуровневый модуль). Он не зависит напрямую от конкретной электростанции или розетки. Вместо этого у него есть **абстракция** — разъем питания (USB-C). Любой блок питания, реализующий этот интерфейс (зарядка от телефона, от ноутбука, порт в самолете), подходит. Детали (напряжение, сила тока, источник энергии) скрыты за интерфейсом. Это и есть DIP в действии.

---

### Вывод

**DIP** — это принцип, который переворачивает привычное мышление «высокоуровневый код знает, какой низкоуровневый использовать». Вместо этого оба уровня смотрят на абстракцию. Это делает вашу архитектуру гибкой, тестируемой и устойчивой к изменениям. Если в проекте сложно что-то переключить или протестировать — скорее всего, нарушен именно DIP.
