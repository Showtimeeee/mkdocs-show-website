# Isolation (Изоляция)

**Isolation (Изоляция)** — свойство транзакций, которое определяет, как изменения одной транзакции видны другим параллельно выполняющимся транзакциям. Каждая транзакция должна выполняться так, как будто она одна работает с базой данных.

#### **Основная концепция**

- Параллельные транзакции не должны мешать друг другу.
- Уровень изоляции определяет, какие "аномалии" допустимы.
- Чем выше уровень изоляции — тем медленнее работа, но надёжнее данные.
- Баланс между производительностью и целостностью данных.

#### **Проблемы параллельного доступа (аномалии)**

| Аномалия | Описание | Пример |
|----------|----------|--------|
| **Dirty Read** (Грязное чтение) | Чтение незафиксированных данных другой транзакции | Транзакция А списала деньги, но не зафиксировала. Транзакция Б видит новый баланс и делает что-то на основе этого |
| **Non-Repeatable Read** (Неповторяемое чтение) | При повторном чтении данные изменились | Транзакция А читает баланс (1000₽), транзакция Б меняет на 500₽, транзакция А читает снова — видит 500₽ |
| **Phantom Read** (Фантомное чтение) | При повторном чтении появляются новые строки | Транзакция А читает все заказы (3 шт.), транзакция Б добавляет новый, транзакция А читает снова — видит 4 шт. |

---

### Уровни изоляции (SQL Standard)

| Уровень | Dirty Read | Non-Repeatable Read | Phantom Read | Описание |
|---------|------------|---------------------|--------------|----------|
| **READ UNCOMMITTED** | ✅ Допустим | ✅ Допустим | ✅ Допустим | Можно читать незафиксированные данные. Быстро, но опасно |
| **READ COMMITTED** | ❌ Нет | ✅ Допустим | ✅ Допустим | Читаем только зафиксированные данные. Самый популярный |
| **REPEATABLE READ** | ❌ Нет | ❌ Нет | ✅ Допустим | При повторном чтении видим те же данные. Используется в MySQL |
| **SERIALIZABLE** | ❌ Нет | ❌ Нет | ❌ Нет | Полная изоляция. Работает как последовательный доступ. Самый медленный |

---

### Пример: Выбор уровня изоляции

```sql
-- Устанавливаем уровень изоляции
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

BEGIN TRANSACTION;

-- Транзакция выполняется с уровнем изоляции READ COMMITTED
SELECT balance FROM accounts WHERE id = 1;  -- Видим только зафиксированные данные

UPDATE accounts SET balance = balance - 1000 WHERE id = 1;

COMMIT;
```

### В Python (с SQLAlchemy)

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

engine = create_engine('postgresql://user:pass@localhost/db')
Session = sessionmaker(bind=engine)

session = Session()
session.execute("SET TRANSACTION ISOLATION LEVEL REPEATABLE READ")

try:
    session.begin()
    # Выполняем операции
    session.commit()
except Exception:
    session.rollback()
```

### Когда какой уровень использовать

| Уровень | Когда использовать |
|---------|-------------------|
| **READ UNCOMMITTED** | Почти никогда. Только для отчётов, где точность не важна |
| **READ COMMITTED** | Стандартный выбор. Баланс скорости и надёжности. Большинство проектов |
| **REPEATABLE READ** | Когда важно, чтобы повторные чтения давали тот же результат (отчёты, аналитика) |
| **SERIALIZABLE** | Финансы, бронирование — где абсолютная точность важнее скорости |

### Блокировки: Пессимистическая vs Оптимистическая

| Тип | Описание | Когда использовать |
|-----|----------|-------------------|
| **Пессимистическая** | Блокируем строку сразу (SELECT ... FOR UPDATE) | Высокий конкурентный доступ, нельзя потерять данные |
| **Оптимистическая** | Проверяем версию перед обновлением (version + 1) | Низкая конкуренция, лучше производительность |

**Пессимистическая блокировка:**

```sql
BEGIN TRANSACTION;

-- Блокируем строку для других транзакций
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;

-- Только эта транзакция может изменить данные
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;

COMMIT;  -- Блокировка снимается
```

**Оптимистическая блокировка:**

```python
class Account(Base):
    __tablename__ = 'accounts'
    id = Column(Integer, primary_key=True)
    balance = Column(Integer)
    version = Column(Integer, default=1)  # Счётчик версий

# При обновлении проверяем версию
session.query(Account).filter(
    Account.id == 1,
    Account.version == old_version
).update({
    'balance': new_balance,
    'version': old_version + 1
})

# Если affected_rows == 0 — кто-то изменил данные, повторяем попытку
```

### Распространённые ошибки

| Ошибка | Почему плохо | Решение |
|--------|-------------|---------|
| **Слишком высокий уровень** | Медленная работа, блокировки | Выбрать READ COMMITTED |
| **Слишком низкий уровень** | Грязные чтения, потеря данных | Повысить уровень |
| **Нет явных блокировок** | Конфликты при обновлении | Использовать FOR UPDATE или версионирование |
| **Долгие транзакции** | Долгие блокировки, дедлоки | Держать транзакции короткими |

---

### Пример из жизни: Бронирование билетов

Два человека одновременно бронируют последнее место в кинотеатре.

- **READ UNCOMMITTED:** Оба видят, что место свободно → продают билеты двум людям ❌
- **SERIALIZABLE:** Один бронирует место, второй ждёт → покупает только один ✅
- **Оптимистическая блокировка:** Оба пытаются обновить, один проигрывает и повторяет попытку ✅

---

### Вывод

**Изоляция** — баланс между скоростью и точностью. 

- **READ COMMITTED** — выбор большинства проектов (быстро + надёжно).
- **SERIALIZABLE** — только для финансов и бронирования (точность важнее скорости).
- Используйте **FOR UPDATE** для пессимистической блокировки при высоком конкурентном доступе.
- Помните: чем выше изоляция, тем медленнее система.
