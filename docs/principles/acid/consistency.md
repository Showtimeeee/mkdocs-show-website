# Consistency (Согласованность)

**Consistency (Согласованность)** — свойство транзакций, которое гарантирует, что после успешного завершения транзакции база данных переходит из одного **согласованного состояния** в другое **согласованное состояние**. Все правила, ограничения и бизнес-логика остаются валидными.

#### **Основная концепция**

- Транзакция должна соблюдать все **бизнес-правила** и **ограничения** базы данных.
- Если транзакция нарушает какое-либо ограничение — она откатывается.
- Это про **правильность данных**, а не про их сохранность (это Durability).

#### **Виды ограничений (Consistency Rules)**

1. **Структурные** — PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL, CHECK.
2. **Бизнес-правила** — баланс не отрицательный, возраст > 0, дата не в прошлом.
3. **Кастомные** — триггеры и хранимые процедуры.

#### **Преимущества**

1. Целостность данных
2. Автоматическая защита от ошибок
3. Предсказуемость и надёжность

---

### Пример: Банковский перевод

**Без согласованности** — можно создать счёт с отрицательным балансом:

```sql
-- ❌ Таблица без ограничений
CREATE TABLE accounts (id INT, balance INT);
INSERT INTO accounts VALUES (1, -500);  -- Отрицательный баланс
```

**С согласованностью** — ограничение не даст вставить плохие данные:

```sql
-- ✅ Таблица с ограничением
CREATE TABLE accounts (
    id INT PRIMARY KEY,
    balance INT CHECK (balance >= 0)
);

INSERT INTO accounts VALUES (1, -500);  -- ❌ Ошибка! Нарушено правило
```

---

### Транзакция с проверками

```sql
BEGIN TRANSACTION;

-- Проверяем условия
SELECT balance FROM accounts WHERE id = 1;  -- Баланс >= суммы?
SELECT stock FROM products WHERE id = 1;    -- Товар есть?

-- Если всё ок — выполняем
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
UPDATE products SET stock = stock - 1 WHERE id = 1;

COMMIT;  -- ✅ Данные согласованны
```

Если любое условие нарушено — **ROLLBACK**:

```sql
-- ❌ Недостаточно товара
ROLLBACK;  -- Откат, данные не повреждены
```

### Когда использовать

| Ситуация | Важность |
|----------|----------|
| **Банки, финансы** | 🔴 Критично |
| **Интернет-магазины** (склад) | 🔴 Критично |
| **Медицина** | 🔴 Критично |
| **Соцсети** | 🟡 Важно |
| **Кэш, логи** | 🟢 Не обязательно |

---

### Лучшие практики

1. **Ограничения в БД** — даже если код ошибочный, БД не даст сохранить плохие данные.
2. **Проверяйте бизнес-правила на уровне приложения** — БД проверяет структуру, код — логику.
3. **Атомарные UPDATE с проверкой**:
   ```sql
   UPDATE products SET stock = stock - 2 
   WHERE id = 1 AND stock >= 2;  -- Если affected_rows = 0 → ошибка
   ```
4. **Используйте транзакции для согласованности** — все изменения в одной транзакции.

---

### Пример из жизни: Покупка авиабилета

**Согласованность:**
- Место не может быть занято дважды.
- У пассажира должен быть документ.
- Стоимость билета не отрицательная.

**Нарушение:** два пассажира получают одно место → хаос.  
**Согласованность:** БД проверяет, что место свободно → только один покупает.

---

### Вывод

**Consistency** — гарантирует, что данные всегда **корректны**: баланс не отрицательный, товар не заканчивается ниже нуля, заказы ссылаются на существующих пользователей. Ограничения в БД + проверки в коде = надёжность.
