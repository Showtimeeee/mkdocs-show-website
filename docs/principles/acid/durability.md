# Durability (Устойчивость)

**Durability (Устойчивость)** — свойство транзакций, которое гарантирует, что после успешного завершения (COMMIT) все изменения **сохраняются навсегда**, даже в случае сбоя системы, отключения питания или перезагрузки.

#### **Основная концепция**

- После COMMIT изменения **фиксируются** и не могут быть потеряны.
- Даже если сервер выключится через 1 секунду после COMMIT — данные сохраняются.
- Устойчивость реализуется через запись изменений на **диск** (журнал, WAL).
- Это про **сохранность данных**, а не про их правильность (это Consistency).

#### **Ключевые механизмы**

1. **Write-Ahead Logging (WAL) / Журнал транзакций**
   - Перед изменением данных записывается лог на диск.
   - При сбое система восстанавливается из лога.

2. **Redo Log / Undo Log**
   - Redo: повторное выполнение операций при восстановлении.
   - Undo: откат незавершённых транзакций.

3. **Синхронные / асинхронные записи**
   - Синхронно: подтверждение только после записи на диск (надёжно, медленно).
   - Асинхронно: подтверждение до записи на диск (быстро, опасно).

4. **Репликация**
   - Копирование данных на несколько серверов для защиты от аппаратных сбоев.

---

### Пример: Как работает WAL

```
1. Транзакция: UPDATE accounts SET balance = 100 WHERE id = 1;

2. Запись в WAL (журнал) на диск:
   "Строка 1: id=1, balance = 100"

3. Только после записи в WAL — данные меняются в памяти/диске

4. COMMIT — система подтверждает, что WAL записан

5. При сбое система читает WAL и восстанавливает все COMMIT-транзакции
```

---

### Настройки устойчивости в PostgreSQL

```sql
-- Параметры durability в postgresql.conf

# Синхронная запись WAL (рекомендуется)
synchronous_commit = on          # ✅ Гарантирует durability
wal_sync_method = fdatasync      # Принудительная запись на диск
checkpoint_timeout = 5min        # Автоматическое сохранение на диск

# Асинхронная запись (опасно для финансов)
synchronous_commit = off         # ❌ Может потерять данные при сбое
```

### Когда важна устойчивость

| Ситуация | Важность |
|----------|----------|
| **Банковские транзакции** | 🔴 Критично. Потеря денег недопустима |
| **Медицинские данные** | 🔴 Критично. Жизни зависят от данных |
| **Интернет-магазины** (заказы) | 🔴 Критично. Потеря заказа = потеря клиента |
| **Соцсети** (посты, лайки) | 🟡 Важно, но потеря некоторых данных допустима |
| **Логи, аналитика** | 🟢 Можно потерять часть логов |
| **Кэш (Redis, Memcached)** | 🟢 Устойчивость не нужна. Это временные данные |

---

### Альтернативы: Синхронная vs Асинхронная репликация

| Тип | Описание | Когда использовать |
|-----|----------|-------------------|
| **Синхронная** | Пока все реплики не подтвердят запись — COMMIT не даём | Финансы, критические данные |
| **Асинхронная** | COMMIT даём сразу, реплики догоняют потом | Высокая нагрузка, некритичные данные |

```sql
-- Настройка синхронной репликации в PostgreSQL
ALTER SYSTEM SET synchronous_standby_names = 'replica1, replica2';
ALTER SYSTEM SET synchronous_commit = 'remote_write';
```

### Лучшие практики

1. **Включайте WAL и синхронную запись**
   - Даже если вы думаете, что сбои бывают редко — они случаются.

2. **Настраивайте регулярные бэкапы**
   - Полные бэкапы + WAL архивы для восстановления на любой момент.

3. **Используйте репликацию для критичных систем**
   - Один сервер может сгореть. Два — уже надёжнее.

4. **Тестируйте восстановление после сбоя**
   - Проверяйте, что резервные копии реально работают.

5. **Храните бэкапы в другом дата-центре**
   - Пожар, наводнение, взлом — физические риски тоже бывают.

### Распространённые ошибки

| Ошибка | Почему плохо | Решение |
|--------|-------------|---------|
| **Нет WAL или он на HDD** | При сбое теряются последние данные | WAL на SSD, синхронная запись |
| **Асинхронная репликация для финансов** | При падении мастера теряются неподтверждённые данные | Использовать синхронную репликацию |
| **Нет бэкапов** | Сбой диска = потеря всего | Делать регулярные бэкапы |
| **Один дата-центр** | Пожар/наводнение — потеря всех данных | Репликация в другой DC |

### Пример из жизни: Авиабилеты

Вы купили авиабилет. Система выдала:
- "Покупка успешна. Билет № 12345"

**Без устойчивости:**
- Через 5 секунд сервер упал. Билет не сохранился. Вы приехали в аэропорт — вас нет в системе. Вы не летите ❌

**С устойчивостью:**
- Транзакция записалась в WAL и на диск. Сервер упал. При восстановлении система прочитала WAL и восстановила ваш билет. Вы летите ✅

---

### Вывод

**Устойчивость (Durability)** — гарантия того, что после COMMIT изменения никогда не будут потеряны. Реализуется через:

1. **WAL (Write-Ahead Log)** — запись на диск до фиксации.
2. **Репликацию** — копирование данных.
3. **Резервное копирование** — защита от физических сбоев.

Без устойчивости любая транзакция может быть потеряна при сбое. Всегда включайте синхронную запись WAL и делайте бэкапы.

## Итог по ACID

| Буква | Свойство | Суть |
|-------|----------|------|
| **A** | Atomicity (Атомарность) | Всё или ничего. Откат при ошибке |
| **C** | Consistency (Согласованность) | Данные всегда валидны (ограничения, бизнес-правила) |
| **I** | Isolation (Изоляция) | Транзакции не мешают друг другу (уровни изоляции) |
| **D** | Durability (Устойчивость) | После COMMIT данные сохраняются навсегда (WAL, репликация) |
