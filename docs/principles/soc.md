# Separation of Concerns (SoC)

**Separation of Concerns (Разделение ответственности)** — каждый модуль, класс или компонент должен отвечать только за **одну чётко определённую задачу**. Разные задачи должны быть разделены между разными частями системы.

#### **Основная концепция**

- Система делится на слои/модули, каждый со своей зоной ответственности.
- Изменение в одной зоне не должно затрагивать другие.
- Смешивание разных задач (UI + бизнес-логика + БД) приводит к хаосу.
- Это **фундамент** для SOLID, KISS, DRY и чистого кода в целом.

#### **Типичные слои**

| Слой | Ответственность | Пример |
|------|-----------------|--------|
| **Презентация** | Отображение данных, UI/API | Контроллеры, шаблоны |
| **Бизнес-логика** | Правила, вычисления, валидация | Сервисы, Use Cases |
| **Данные** | Работа с БД | Репозитории, DAO |
| **Инфраструктура** | Кэш, логи, безопасность | Декораторы, middleware |

#### **Преимущества**

- Читаемость — каждый модуль понятен.
- Поддерживаемость — изменения локализованы.
- Переиспользуемость — бизнес-логика не привязана к UI.
- Тестируемость — каждый слой тестируется отдельно.

---

### Пример: Нарушение SoC

```python
# ❌ Всё в одном классе: и БД, и HTML, и логика
class Order:
    def calculate_total(self): ...       # Бизнес-логика
    def save_to_db(self): ...            # Работа с БД
    def render_html(self): ...           # Генерация HTML
```

**Проблемы:** Нельзя переиспользовать логику, сложно тестировать, любое изменение ломает всё.

---

### Пример: Соблюдение SoC

```python
# ✅ Чёткое разделение по слоям

# Слой данных
class OrderRepository:
    def save(self, order_data): ...

# Бизнес-логика
class OrderService:
    def __init__(self, repo: OrderRepository): ...
    def create_order(self, items, user): ...

# Презентация (API/UI)
class OrderController:
    def __init__(self, service: OrderService): ...
    def create_order_endpoint(self, request): ...
```

**Теперь можно:** заменить БД (поменять `OrderRepository`), добавить API вместо HTML (контроллер возвращает JSON), тестировать бизнес-логику без БД.

---

### Реальные архитектуры с SoC

| Архитектура | Разделение |
|-------------|-----------|
| **MVC** | Model (данные), View (UI), Controller (логика) |
| **Clean Architecture** | Entities → Use Cases → Controllers → UI/DB |
| **Layered Architecture** | Presentation → Business → Data → Infrastructure |

---

### Связь с другими принципами

| Принцип | Как связан |
|---------|-----------|
| **SRP** (SOLID) | Частный случай SoC на уровне класса |
| **DIP** (SOLID) | Зависимости между слоями через абстракции |
| **KISS** | Разделение упрощает каждый модуль |
| **DRY** | Общие знания выносятся в нужный слой |

---

### Лучшие практики

1. **Чётко определите слои** и их границы.
2. **Запретите "перепрыгивание"** — UI не обращается напрямую к БД.
3. **Используйте Dependency Injection** для передачи зависимостей.
4. **Тестируйте слои изолированно** (бизнес-логика без БД).

---

### Пример из жизни: Ресторан

| Слой | В ресторане | В коде |
|------|-------------|--------|
| Клиент | Посетитель | UI/API |
| Официант | Принимает заказ | Контроллер |
| Повар | Готовит блюдо | Бизнес-логика |
| Кладовщик | Выдаёт продукты | Слой данных |
| Холодильник | Хранит продукты | База данных |

**Нарушение:** Повар сам бегает в кладовку за продуктами.  
**SoC:** Каждый делает свою работу.

---

### Вывод

**SoC** — фундамент чистой архитектуры. Разделяйте систему на независимые слои: презентация, бизнес-логика, данные, инфраструктура. Это делает код понятным, тестируемым и поддерживаемым.

**Главное правило:** каждый модуль — одна задача. Без этого SOLID, KISS и DRY не работают.
