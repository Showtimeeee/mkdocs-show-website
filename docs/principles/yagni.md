# Принцип YAGNI

**YAGNI (You Aren't Gonna Need It)** — принцип разработки программного обеспечения, который гласит: **не добавляйте функциональность, пока она вам действительно не понадобится**. Не пишите код «на будущее», не проектируйте систему с запасом на несуществующие требования.

#### **Основная концепция**

Суть принципа заключается в том, что:
- Разработчики часто ошибаются в прогнозах о том, какая функциональность понадобится в будущем.
- Код, написанный «на всякий случай», скорее всего никогда не будет использован.
- Такой код усложняет систему, требует поддержки и тестирования, но не приносит ценности.
- Добавляйте новый функционал **только когда он нужен прямо сейчас**.

> **Важно:** YAGNI — это не про лень. Это про **эффективное использование времени и ресурсов**. Вы не экономите время, написав код заранее — вы его теряете на поддержку ненужной функциональности.

#### **Преимущества использования**

1. **Меньше кода**
   - Меньше кода = меньше багов, меньше времени на поддержку, быстрее загрузка.
2. **Простота архитектуры**
   - Система содержит только то, что реально нужно, и не переусложнена.
3. **Быстрая разработка**
   - Вы не тратите время на то, что может никогда не пригодиться.
4. **Гибкость**
   - Проще изменить простую систему, чем ту, в которой тысячи строк мёртвого кода.
5. **Снижение когнитивной нагрузки**
   - Разработчики не пытаются понять, зачем нужен тот или иной код.

#### **Ключевые признаки нарушения YAGNI**

1. **Параметры и конфиги «на будущее»**
   - Добавлены параметры, которые никогда не используются, но усложняют API.
2. **Преждевременная оптимизация**
   - Кэширование, индексы, многопоточность там, где нагрузка этого не требует.
3. **«На всякий случай»**
   - Функции, классы, поля, которые могут когда-нибудь пригодиться.
4. **Избыточная параметризация**
   - Методы с 10 параметрами, где 9 из них всегда передают дефолтные значения.
5. **Генерализация раньше времени**
   - Написание универсального решения для всех случаев, когда нужно решить одну конкретную задачу.

### Пример: Система отправки уведомлений

Представьте, что вы разрабатываете систему уведомлений для интернет-магазина. Сейчас нужно отправлять только **email** при оформлении заказа.

#### **Нарушение YAGNI («на будущее»)**

```python
from abc import ABC, abstractmethod
from typing import List, Dict, Optional

class NotificationChannel(ABC):
    @abstractmethod
    def send(self, recipient: str, message: str, **kwargs):
        pass

class EmailChannel(NotificationChannel):
    def send(self, recipient: str, message: str, **kwargs):
        print(f"Отправка email на {recipient}: {message}")

class SmsChannel(NotificationChannel):
    def send(self, recipient: str, message: str, **kwargs):
        # TODO: реализовать позже
        print(f"Отправка SMS на {recipient}: {message}")

class PushChannel(NotificationChannel):
    def send(self, recipient: str, message: str, **kwargs):
        # TODO: реализовать позже
        print(f"Отправка Push на {recipient}: {message}")

class NotificationManager:
    def __init__(self):
        self.channels: Dict[str, NotificationChannel] = {
            'email': EmailChannel(),
            'sms': SmsChannel(),    # Не используется!
            'push': PushChannel()   # Не используется!
        }
    
    def send_notification(
        self, 
        recipient: str, 
        message: str, 
        channel_type: str = 'email',
        priority: Optional[int] = None,     # Никогда не используется
        retry_count: Optional[int] = None,  # Никогда не используется
        template_id: Optional[str] = None,  # Никогда не используется
        attachments: Optional[List[str]] = None  # Никогда не используется
    ) -> bool:
        
        channel = self.channels.get(channel_type)
        if not channel:
            return False
        
        channel.send(recipient, message)
        return True

# Использование
manager = NotificationManager()
manager.send_notification("user@example.com", "Ваш заказ оформлен!")
```

Проблема:
- 3 класса вместо 1 (`SmsChannel` и `PushChannel` никогда не используются).
- 5 параметров метода, из которых реально используются только 2.
- Архитектура сложнее, чем нужно.
- 50+ строк кода вместо 10.

#### **Соблюдение YAGNI (только нужное сейчас)**

```python
class EmailNotifier:
    def send_email(self, recipient: str, message: str):
        print(f"Отправка email на {recipient}: {message}")

class OrderService:
    def __init__(self):
        self.notifier = EmailNotifier()
    
    def place_order(self, user_email: str, order_id: int):
        # Логика оформления заказа...
        self.notifier.send_email(user_email, f"Ваш заказ {order_id} оформлен!")

# Использование
service = OrderService()
service.place_order("user@example.com", 12345)
```

Теперь:
- Только то, что нужно прямо сейчас.
- 10 строк кода вместо 50.
- Если понадобятся SMS или Push — добавим их **когда это станет требованием**.
- Код простой, понятный, лёгкий в поддержке.

### Когда использовать YAGNI (и когда нарушать)

| Ситуация | Что делать |
|----------|-----------|
| **Вы точно знаете, что функциональность понадобится через неделю** | Можно сделать базовую структуру, но не реализовывать полностью |
| **Вы предполагаете, что функциональность когда-нибудь понадобится** | YAGNI — не делайте сейчас |
| **Вы пишете библиотеку/фреймворк для других** | YAGNI менее применим — нужно больше гибкости |
| **Вы разрабатываете публичное API** | Нужно проектировать с запасом, чтобы не ломать совместимость |
| **Крупный enterprise-проект с долгосрочным планированием** | Можно делать базовое архитектурное решение, но детали — по мере необходимости |
| **Прототип или MVP** | YAGNI обязателен — делайте минимум |

### Лучшие практики

1. **Пишите код для текущей итерации**
   - Спросите себя: «Нужно ли это для завершения текущей задачи?» Если нет — не пишите.
2. **Используйте правило трёх (Rule of Three)**
   - Если функциональность понадобилась в третий раз — только тогда абстрагируйте.
3. **Рефакторинг вместо планирования**
   - Проще переписать простой код, чем поддерживать ненужную сложность.
4. **Удаляйте мёртвый код**
   - Комментарии типа `# TODO: реализовать позже` часто остаются навсегда. Лучше удалить.
5. **Задавайте вопрос «Зачем?»**
   - Прежде чем добавить параметр, класс или метод, спросите: «Зачем это сейчас?»
6. **Меньше абстракций на старте**
   - Начинайте с конкретных решений. Обобщайте только когда видите реальный паттерн.

### Альтернативы и дополнения

1. **KISS (Keep It Simple, Stupid)**
   - Близкий принцип: держите систему простой.
2. **DRY (Don't Repeat Yourself)**
   - Если видите повтор — выносите, но не делайте это раньше времени.
3. **AHA (Avoid Hasty Abstractions)**
   - Современная эволюция YAGNI: не абстрагируйтесь слишком рано.
4. **BDUF (Big Design Up Front)**
   - Антипод YAGNI — детальное проектирование всего заранее. Часто приводит к оверинжинирингу.

## Пример из жизни: Покупка кухонного комбайна

Вы покупаете кухонный комбайн. В нём 20 насадок: для взбивания, для теста, для шинковки, для картофеля-фри, для сока, для мясорубки...

Вы готовите **только супы и салаты**. Вам нужна одна ножевая насадка и одна для шинковки. Остальные 18 насадок пылятся в шкафу. Они занимают место, усложняют уборку, вы случайно можете порезаться о неиспользуемую насадку.

В программировании то же самое: неиспользуемые классы, методы и параметры — это насадки, которые пылятся в вашем коде. Вы за них платите (временем на понимание, тестирование и поддержку), но они не приносят ценности.

### YAGNI vs DRY: Борьба или баланс?

Часто возникает конфликт между DRY и YAGNI.

| Принцип | Что говорит |
|---------|-------------|
| **DRY** | Не повторяйся. Если код повторяется — вынеси в общее место. |
| **YAGNI** | Не пиши код «на будущее». Делай только то, что нужно сейчас. |

**Как совмещать?**

1. **Не абстрагируйтесь рано** (YAGNI).
2. **Если видите третий повтор** (Rule of Three) — выносите (DRY).
3. **Не создавайте универсальных решений** (YAGNI) — решайте конкретную задачу, но без дублирования.

**Пример баланса:**

```python
# Нарушение YAGNI: универсальный валидатор «на будущее»
class UniversalValidator:
    def validate(self, value, rules):
        # 100 строк универсальной логики
        pass

# Нарушение DRY: повторяющаяся валидация
if len(email) > 0 and '@' in email:
    # ...
if len(phone) > 0 and phone.isdigit():
    # ...

# ✅ Баланс: конкретные функции для конкретных нужд
def validate_email(email: str) -> bool:
    return '@' in email and len(email) > 0

def validate_phone(phone: str) -> bool:
    return phone.isdigit() and len(phone) == 11
```

### Заблуждения о YAGNI

| Заблуждение | Правда |
|-------------|--------|
| YAGNI = никогда не планируй | Нет, планировать нужно архитектуру, но не реализовывать детали |
| YAGNI = ленивый подход | Нет, это подход к эффективному использованию ресурсов |
| YAGNI противоречит SOLID | Нет, SOLID о структуре, YAGNI о необходимости функционала |
| YAGNI работает только в Agile | Нет, он работает в любой методологии, но особенно в Agile |
| Я всё равно потрачу время потом | Часто функциональность вообще не понадобится. Вы сэкономили время |

---

### Вывод

**YAGNI** — это дисциплина, которая защищает вас от **оверинжиниринга**. Вместо того чтобы строить сложные архитектуры «на будущее», вы решаете одну конкретную задачу и решаете её хорошо. Когда появляется новая задача — вы расширяете систему.

> **Самый эффективный код — тот, который не написан.**

Не пишите код «на всякий случай». Не добавляйте параметры, которые не используются. Не создавайте классы «для будущих расширений». Доверяйте реальным требованиям, а не своим предположениям. Ваш код станет проще, надёжнее и дешевле в поддержке.
