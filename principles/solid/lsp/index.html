    Liskov Substitution Principle (LSP)

    Liskov Substitution Principle (Принцип подстановки Барбары Лисков) — объекты в программе должны быть заменимы на экземпляры их подтипов без изменения правильности выполнения программы.

    Основная концепция

    Суть принципа заключается в том, что: - Если у вас есть родительский класс Parent и дочерний Child, то вы должны иметь возможность использовать Child везде, где используется Parent, и программа не сломается. - Наследование должно выражать отношение «is-a» (является), а не просто «я хочу переиспользовать код». - Дочерний класс не должен требовать от вызывающего кода чего-то, что не требовал родитель.

    Преимущества использования

    1. Надежность кода
    2. Можно безопасно расширять систему через наследование.
    3. Предсказуемость поведения
    4. Полиморфизм работает так, как ожидается.
    5. Облегчение рефакторинга
    6. Замена одного класса на другой не ломает логику.
    7. Чистая архитектура
    8. Иерархия наследования становится логичной и понятной.

    Ключевые правила (условия LSP)

    1. Нельзя усиливать предусловия
    2. Если родительский метод принимает любой int, дочерний не должен требовать только положительное число.
    3. Нельзя ослаблять постусловия
    4. Если родитель гарантирует возврат числа, дочерний не должен возвращать None.
    5. Инварианты родителя должны сохраняться
    6. Все свойства родителя, которые всегда истинны, должны быть истинны и у потомка.
    7. Историческое ограничение
    8. Дочерний класс не должен изменять состояние объекта так, как не мог бы родитель.

    Пример: Прямоугольник и Квадрат

    Классический пример нарушения LSP — наследование Square от Rectangle.

    Нарушение LSP

    class Rectangle:
    def __init__(self, width: int, height: int):
        self._width = width
        self._height = height

    def set_width(self, width: int):
        self._width = width

    def set_height(self, height: int):
        self._height = height

    def get_area(self) -> int:
        return self._width * self._height

class Square(Rectangle):
    def __init__(self, side: int):
        super().__init__(side, side)

    def set_width(self, width: int):
        self._width = width
        self._height = width  # Квадрат вынужден менять обе стороны!

    def set_height(self, height: int):
        self._height = height
        self._width = height  # Квадрат вынужден менять обе стороны!

# Клиентский код, который работает с Rectangle
def resize_and_print_area(rect: Rectangle):
    rect.set_width(5)
    rect.set_height(10)
    print(f"Площадь: {rect.get_area()}")  # Для Rectangle: 50. Для Square: 100!

square = Square(4)
resize_and_print_area(square)  # Ожидаем 50? Получаем 100 — поведение сломано!

    Проблема: для прямоугольника площадь стала 5×10=50, а для квадрата — 10×10=100. Квадрат нельзя подставить вместо прямоугольника — программа ведет себя неожиданно.

    Соблюдение LSP

    Правильное решение — не наследовать Square от Rectangle. Вместо этого — сделать общего предка Shape.

    from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def get_area(self) -> int:
        pass

class Rectangle(Shape):
    def __init__(self, width: int, height: int):
        self.width = width
        self.height = height

    def set_width(self, width: int):
        self.width = width

    def set_height(self, height: int):
        self.height = height

    def get_area(self) -> int:
        return self.width * self.height

class Square(Shape):
    def __init__(self, side: int):
        self.side = side

    def set_side(self, side: int):  # Свой метод, а не set_width/set_height
        self.side = side

    def get_area(self) -> int:
        return self.side * self.side

# Теперь ожидание единое: оба просто умеют вычислять площадь
def print_area(shape: Shape):
    print(f"Площадь: {shape.get_area()}")

print_area(Rectangle(5, 10))  # 50
print_area(Square(4))         # 16 — все корректно

    Когда использовать наследование (а значит, LSP важен)

    1. Когда дочерний класс действительно является подтипом родителя
    2. Птица → Сокол (да). Птица → Пингвин (вопрос: пингвин не летает, а Bird::fly() есть — нарушение LSP).
    3. Когда поведение потомка не противоречит поведению родителя
    4. Все гарантии родителя соблюдены.

    Лучшие практики

    1. Тест на подстановку
    2. Попробуйте в уме заменить родителя на потомка. Если поведение меняется неожиданно — LSP нарушен.
    3. Предпочитайте композицию наследованию
    4. Часто LSP нарушается именно из-за форсированного наследования «ради переиспользования методов».
    5. Не выбрасывайте новые исключения
    6. Если родительский метод не бросал исключение, дочерний тоже не должен (или бросать то же самое).

    Альтернативы и дополнения

    1. Composition over Inheritance
    2. Вместо Square extends Rectangle сделайте Rectangle и Square независимыми, вынесите общее в интерфейс.
    3. Design by Contract (DbC)
    4. Формальное описание предусловий, постусловий и инвариантов помогает соблюсти LSP.

    Пример из жизни: Транспортные средства

    Представьте, что у вас есть класс ТранспортноеСредство с методом завести_двигатель(). Вы создаете дочерний класс Велосипед (у которого нет двигателя). Если подставить Велосипед вместо ТранспортногоСредства, вызов завести_двигатель() сломается. Это нарушение LSP.

    Правильная иерархия: ТранспортноеСредство без метода завести_двигатель, а подтипы СДвигателем и БезДвигателя.

    Вывод

    LSP — это принцип, который защищает вас от «сюрпризов» при использовании полиморфизма. Он говорит: наследование — это серьезный контракт. Если подставить потомка вместо родителя, всё должно работать так же хорошо. Если не работает — значит, вы использовали наследование неправильно, и лучше выбрать композицию или перепроектировать иерархию.
